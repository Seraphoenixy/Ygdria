# 附件存储协议

本协议定义附件元数据与物理文件之间的边界。表字段、共享引用模型和外键见 [数据模型](data-model.md#3-表定义)；运行维护与 `doctor` 见 [运行与维护](operations.md)。

## 1. 存储边界

- 数据库只保存受控相对 `storage_key`，不得保存绝对路径、盘符、反斜杠或 `..`。
- 正式文件位置由存储适配器以 `<storage-root>/<storage_key>` 解析；`storage_key` 使用 `attachments/<uuid>`。
- 原始文件名仅是元数据，不参与真实路径计算。
- 每个附件实体独占一份物理文件；多个笔记通过正文 JSON 中的引用关联同一附件实体。

## 2. 写入流程

1. **上传与准备**：上传文件到临时目录。
2. **校验**：对临时文件进行大小、MIME 类型及内容哈希校验。
3. **准备存储**：生成不可由用户控制的 `attachments/<uuid>` 存储键，将文件原子重命名（move）到正式存储目录；原始文件名只保存为元数据。
4. **数据库更新**：在 SQLite 事务中插入附件元数据记录。
5. **异常处理**：若数据库事务失败，必须删除第 3 步移动后的正式文件。

## 3. 关联与删除流程

1. **解除关联**：用户从笔记移除附件时，删除笔记正文中的附件引用，绝不直接删除共享附件实体。
2. **最后一个引用**：仅当附件不再被任何笔记正文引用时，才在同一数据库事务中删除 `attachments` 元数据并写入 `storage_cleanup_jobs`。
3. **物理清理**：后台任务在提交后删除物理文件；失败时增加尝试次数并保留错误，等待下次重试。

## 4. 补偿与定期清理

系统应提供后台补偿任务（例如应用启动时或空闲时间），扫描受控 `attachments/` 根目录中的孤儿文件，并登记到 `storage_cleanup_jobs`。任务执行前必须再次确认该 `storage_key` 不存在于 `attachments`，避免并发重新关联时误删文件。

`ygdria doctor` 校验附件文件是否存在、是否仍位于存储根内、大小与 SHA-256 是否与元数据一致；`doctor --fix` 只会清理专用临时上传目录，不会删除正式附件文件或附件元数据。
